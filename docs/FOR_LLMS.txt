1. NON-NEGOTIABLE OPERATOR RULES
--------------------------------
- The robot has no internet. The operator uses the Windows deploy tool, which
  bundles the committed branch and copies it to the robot. Never tell the
  operator to run `git pull` on the robot. Say “update the robot” and provide
  only robot-side commands to run after deployment.
- Work on the RIGHT arm: `working_arm=right`, TCP/IK frame `tip_r`, right
  gripper scope, and physical-right wrist stream `wrist_a`.
- The claw cannot be operated manually. Use the supervised software
  calibration/jog procedures; do not instruct the operator to hand-teach the
  claw.
- The board may move or rotate between runs. A fresh head image and live board
  registration are required for task motion. Do not assume yesterday’s board
  pose remains valid.
- Calibration results take priority over planned feature work. Incorporate a
  new physical measurement into the runtime config/fallback before proceeding.
- Never extrapolate a single physical motion into a large trajectory without a
  fresh preview and operator inspection.
- IK/motion errors must not create an infinite retry loop. Recovery may move to
  the validated camera-clear pose, capture a new image, and ask the operator
  whether to retry. “no” exits cleanly.
- Do not ask whether to move to RIGHT_READY. After a board image, move there
  automatically. In location testing, `r` means “retake the board image only”
  (the board may have moved), then return to RIGHT_READY and show the next
  location prompt.
- Direct flags are preferred when repeating a single action:
  `--recalibrate`, `--test-positions`, and `--competition-task`.
- Use the hardware E-stop during physical work. The runtime may clear the
  software E-stop on connect, but it must still refuse a pressed hardware
  E-stop.

4. DEPLOYMENT AND BASIC COMMANDS
--------------------------------
From the development machine, deploy the committed branch with the existing
PowerShell tool (it pulls locally, creates a bundle, copies it, and runs the
robot preflight):
  `tools/deploy_vega.ps1`
The robot checkout is `~/ROCO-SteadyHand-live`.

After updating the robot, run commands from that checkout with Conda `python3`
for arm/head control. Wrist-camera tools use `/usr/bin/python3` when they need
the system `wrist_cameras` bindings.

No-motion/local checks:
  python3 -m unittest discover -s tests -v
  python3 -m py_compile tools/vega_competition_pipeline.py
  python3 tools/vega_preflight.py

Main entry point (menu):
  python3 tools/vega_competition_pipeline.py \
    --confirm-head-motion --confirm-physical-motion

Direct actions:
  # Five-point calibration after the board has moved
  python3 tools/vega_competition_pipeline.py --recalibrate \
    --confirm-head-motion --confirm-physical-motion

  # Test selected corrected board/task points (no menu)
  python3 tools/vega_competition_pipeline.py --test-positions \
    board.center board.top_right task.battery_size1.pick \
    --clearance-mm 100 --confirm-head-motion --confirm-physical-motion

  # Preflight the same selection without arm motion
  python3 tools/vega_competition_pipeline.py --check-only \
    --test-positions board.center task.battery_size1.pick \
    --confirm-head-motion --confirm-physical-motion

  # Preserve/use a named competition version
  python3 tools/vega_competition_pipeline.py \
    --competition-task battery_size1_pick_v0 \
    --confirm-head-motion --confirm-physical-motion

The position-test menu captures a fresh downward head image first, automatically
moves to RIGHT_READY, then prompts for a destination. At a reached location it
offers every available target, `r` (fresh image/re-register/RIGHT_READY), and
`e` (exit). It does not rerun the five-point calibration on `r`.

5. CALIBRATION PROCEDURE
------------------------
Canonical tool:
  `tools/vega_board_five_point_calibrate.py`
It clears the right arm for a downward head image, points the head down,
captures the board, visits CENTER/TOP_RIGHT/BOTTOM_RIGHT/BOTTOM_LEFT, lets the
operator jog the TCP parallel to the board, asks for TCP-to-board clearance in
millimetres, fits the surface, and writes the live JSON. No manual claw motion
is required.

The lower-level manual-ready route remains available:
  python3 tools/vega_board_manual_calibrate.py \
    --use-configured-right-ready --confirm-physical-motion
It records the seven right-arm joints and modeled `tip_r` pose. The old far
Y reference is optional; the calibrated frame derives the missing top-left
corner. Large automatic shoulder chains are not allowed.

If initial IK is transiently unreachable, the five-point tool performs one
complete recovery attempt at a time (camera-clear, fresh head image, replan)
and asks `Retry calibration?`. A negative answer returns a nonzero status; it
never loops silently.

7. WRIST AND BATTERY BRING-UP
-----------------------------
The preferred precision tool is:
  `tools/vega_wrist_fine_center.py`
It assumes the right TCP is already at a safe low hover, uses only `wrist_a`,
fits a measured 2x2 image Jacobian with reversible small X/Y probes, keeps Z and
orientation fixed, and stops before gripping. Image-center convergence is only
a servo-mechanics test; it is not a jaw-alignment calibration.

Battery source localization is operator-assisted and does not move the robot:
  `tools/vega_battery_size1_source_localize.py capture ...`
  `... homography ...` (explicit four corners and board dimensions)
  `... board-offset ...` (operator supplies measured board-relative mm)
The preferred mapping is same-image four-corner homography -> metric board
offset -> calibrated base XY. It must not infer identity from part count/order.
The source-localization bridge uses the same fixed 386 mm span. Do not
introduce alternate board-size constants in new tools.

Coarse hover bridge:
  `tools/vega_battery_size1_coarse_hover.py`
It validates localization provenance, board-unchanged confirmation, accepted
hover Z/orientation, and moves XY only. It never descends, grips, or places.

Battery jaw/grasp teaching:
  `tools/vega_battery_size1_calibrate.py init --force`
  capture a goal image with `capture-goal-image`, record the taught jaw pixel
  with `record-goal-pixel`, then teach grasp Z with `record-grasp-z`.
  `tools/vega_battery_size1_center.py` performs wrist centering.
  `tools/vega_battery_size1_pick.py` performs the gated open/descend/grip/lift
  attempt only after a complete right-arm calibration exists.
The repository has only `calibration/battery_size1_grasp.template.json`; no
physical jaw goal or grasp height has yet been accepted. No battery pick/place
success is claimed by this handoff.

9. SAFETY AND UNRESOLVED LIMITS
-------------------------------
- The compact Pinocchio model has no collision meshes. IK convergence is not a
  collision guarantee; preflight and operator inspection remain required.
- The configured floor is a conservative bring-up guard, not a newly measured
  claw-contact transform. The physical claw center and modeled `tip_r` are not
  interchangeable without a measured tool transform.
- Board camera corrections and the fitted plane are valid for the current
  calibration process. A moved board requires a fresh image; a new physical
  surface/height result requires the five-point process. The `r` retake path
  may update XY only when image scale/aspect/rotation remains compatible with
  the calibration image; otherwise it stops and asks for full calibration.
- Battery source localization and task motion consume the same canonical board
  calibration loader. The dated record is accepted only when it explicitly
  contains `permanent_fallback: true`; live records still require freshness.
  Runtime board axes are rigid orthonormalized while raw measured vectors and
  angular residual are retained for audit.
- The head camera and wrist camera timestamps use different clock conventions;
  do not fuse them as hardware-synchronized measurements.
- Gripper control is through the vendored DexMate setup driver, right scope,
  grip current 1.0 A and speed 240 deg/s. Driver/retention and placement
  success still require physical validation.
- Wrench units/frame, insertion force thresholds, destination/place Z, and
  part-specific `T_part_tcp` transforms remain uncalibrated.
- The old left-arm tools and generic wrist tool remain in the repository as
  compatibility/diagnostic paths; new physical work must use the right-arm
  contract above.

10. COMPACT HISTORY / WHY THESE VALUES EXIST
--------------------------------------------
- Initial startup used a folded right shoulder near a joint limit. The
  supervised +0.10 rad J1 test validated the positive shoulder-opening
  direction and the tracked FK locally.
- Several early automatic verticalization/IK attempts failed or reached random
  points. The solution was measured RIGHT_READY and RIGHT_CAMERA_CLEAR joint
  presets, explicit downward head motion, camera-clear before every image, and
  supervised five-point board correction.
- A first corner survey found approximately 85 mm TCP clearance at TOP_RIGHT
  and contact at BOTTOM_RIGHT. The requested angular/height correction was
  encoded in the active config and the initial targets were biased so the
  operator starts each reference near 100 mm clearance.
- Repeated calibration runs then produced the permanent fallback record; the
  operator reported the final calibration perfect. Keep the fallback in sync
  with any future accepted physical run.
- The location-test workflow was changed so `r` retakes only the board image,
  all selections move immediately, and RIGHT_READY is automatic after capture.
- Head scene perception was validated offline and then live on consecutive
  frames. Board localization must remain independent of how many parts are on
  the board.
- Wrist cameras were initially blocked by boot/runtime setup, then came live
  after combined boot. The operator visually confirmed `wrist_a` right and
  `wrist_b` left; startup-black frames remain a normal condition.
